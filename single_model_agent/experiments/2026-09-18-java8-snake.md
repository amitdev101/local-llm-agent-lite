# Java 8 Snake Agent Experiment — 2026-09-18

## Executive result

This experiment had two different outcomes that must not be conflated:

| Outcome | Result | Meaning |
|---|---|---|
| End-to-end local-model agent run | **Failed** | Qwen3.5-9B did not independently produce, repair, compile, and finish a correct game. |
| Controller safety behavior | **Passed** | Invalid actions, failed builds, and unsupported completion claims did not become success. |
| Final Java artifact | **Passed compile/static review after independent repair** | Another repair agent rewrote the source; Java 8 compilation and independent static review passed. |
| Interactive gameplay | **Not verified** | The Swing window was not manually played through on a desktop. |

The final example is [`../generated_examples/java8_snake/SnakeGame.java`](../generated_examples/java8_snake/SnakeGame.java).

## Why this experiment existed

The earlier hello-world run proved that Qwen3.5 could complete a short sequence:

```text
edit_file → approval → run_check(lint) → finish
```

That did not prove the agent could handle a realistic coding loop. A Snake game exercises:

- A long source response.
- Several related behavioral requirements.
- Java 8 language/API constraints.
- Compile-error repair.
- Multiple tool turns.
- Context growth and compaction.
- Controller completion evidence.
- Semantic correctness beyond compilation.

## Requested behavior

The model was asked to create a single-file Java 8 Swing game with:

- EDT construction.
- `javax.swing.Timer` game loop.
- Arrow and WASD controls through `WHEN_IN_FOCUSED_WINDOW` key bindings.
- Direct and rapid reversal protection.
- Fixed-grid movement and grid-to-pixel rendering.
- Correct length, growth, score, wall collision, self-collision, and moving-tail behavior.
- Food placed only on empty cells.
- A finite full-board/win state.
- Visible score and game-over/restart instructions.
- Enter restart without duplicate timers.
- Packed, non-resizable layout.
- Java 8 compilation before `finish`.

The prompt explicitly required exactly one action per response and instructed the model to repair
compiler failures before finishing.

## Run A — initial creation

Run id recorded during audit:

```text
run-a68d1ef610044c10
```

### Timeline

1. The first model response contained `edit_file`, `run_check`, and `FINAL` in one response.
2. The parser rejected it with `Expected exactly one ACTION block`.
3. The model retried with one `edit_file` action.
4. The user approved the exact diff.
5. The controller created a checkpoint, applied the file, and verified its content hash.
6. The model requested `run_check(kind=build)`.
7. The user approved the exact Java compiler invocation.
8. Java 8 compilation failed with 16 errors, including missing collection imports, private field
   access, invalid `Color.LIME`, and broken food access.
9. The model replaced the file with a compile-oriented repair.
10. Instead of requesting the next build normally, the model copied the controller's synthetic
    history representation:

    ```text
    <PRIOR_ACTION>{"tool":"run_check","arguments":{"kind":"build"}}</PRIOR_ACTION>
    ```

11. The parser treated that text as a final response rather than a tool action.
12. The completion controller rejected it because the required build was still failed.
13. The model repeated the same pattern. The run was stopped rather than spending more slow turns.

### Correct controller behavior

- The multi-action response never executed partially.
- No write occurred before approval.
- The write had a checkpoint and verified post-write hash.
- The compiler command came from controller policy, not model text.
- The failed compiler output was returned to the model and preserved in events.
- The false success path was rejected because build evidence was absent.
- No path outside the workspace was touched.

### Model/source problems

The first implementation was not merely syntactically broken. It also contained semantic defects:

- Grid coordinates and pixel coordinates were mixed.
- Direction state did not consistently control movement.
- Food placement was not reliably snake-aware.
- Growth/tail removal was incorrect.
- Input focus was unreliable.
- Restart could create a new timer.
- Full-board behavior was not correctly defined.

The compile-oriented repair fixed only part of the surface problem.

### Performance

The independent log audit estimated that six model responses consumed roughly 34 minutes. Maximum
observed first-token latency was about 319 seconds. The run did not reach a valid terminal success.

## Run B — focused repair

Run id recorded during audit:

```text
run-89a928463a144fe4
```

### Timeline

1. The model correctly called `read_file` twice to retrieve the complete source.
2. It identified several genuine behavioral problems.
3. It replaced the file after approval and content verification.
4. The replacement still used `KeyListener`, placed food without checking the snake, recreated the
   timer on restart, rendered snake grid coordinates as pixels, and mishandled movement/growth.
5. It also introduced two Java compilation failures:
   - `Color.DARK_GREEN` does not exist.
   - `Timer.isStopped()` does not exist.
6. The approved Java build failed with those two errors.
7. Context crossed the compaction threshold.
8. The old compactor archived the history but increased the active estimate:

   ```text
   6875 tokens before compaction
   7128 tokens on the next prepared prompt
   ```

9. The next model call became too slow and was terminated at a durable boundary.

### Performance

- One response took approximately 713 seconds, with the first token around 320 seconds.
- Another took approximately 516 seconds, with the first token around 509 seconds.
- Reading the source and retaining large diffs/compiler observations dominated prompt evaluation.

This showed that first-token delay was primarily prompt ingestion/context management, not a
stateless/stateful distinction.

## Defects discovered in the agent

### 1. Qwen3.5 orphan thinking boundary

Some llama.cpp Qwen3.5 templates consume the opening `<think>` token but leave `</think>` in the
generated text. Otherwise-valid actions were rejected as unbalanced.

Resolution:

- Only the Qwen3.5 adapter accepts exactly one orphan closing boundary.
- Only the suffix is parsed.
- Repeated or otherwise unbalanced thinking tags remain invalid.

### 2. Synthetic prior-action imitation

The controller inserted `<PRIOR_ACTION>...</PRIOR_ACTION>` as an assistant message. The model
learned/copy-pasted that internal representation instead of the public `ACTION:` contract.

Resolution:

- Synthetic assistant-side prior-action markup was removed.
- The following typed observation already records the tool, status, and evidence.
- This reduces both imitation risk and active prompt size.

### 3. Compaction increased context

The old implementation retained up to eight recent messages, then added another summary. With a
short history containing very large messages, compaction grew rather than shrank the prompt.

Resolution:

- Archive the full history first.
- Keep controller state plus at most three recent messages.
- Bound each retained message to 4,096 characters.
- Record before/after token estimates.
- A disposable validation reduced an artificial history from 27,447 to 3,554 estimated tokens.

### 4. Semantic phrases became required paths

The deterministic requirement parser classified slash-shaped phrases such as
`game-over/restart` and `wall/self` as file paths. Completion would then require nonexistent files.

Resolution:

- Only candidates with recognized source/config filename suffixes become expected artifacts.
- A successful mutation still supplies the actual changed paths dynamically.

### 5. Misleading event step numbers

Internal `CheckpointCreated` and `EditApplied` events used step zero even when caused by a later
agent step.

Resolution:

- The active step now propagates into tool execution and mutation events.

### 6. Passing checks could become stale

A passing build/lint result could remain in controller state after a later source edit.

Resolution:

- Every verified source edit marks all existing checks `STALE`.
- `ChecksInvalidated` is a critical, fsynced event.
- Resume replays invalidations.
- A fake-provider sequence proved that `pass → edit → finish` is rejected until a new check passes.

## Final artifact repair

The real local-model experiment was stopped and recorded as failed. A separate repair agent then
rewrote the example rather than pretending the Qwen run had succeeded.

The repaired source implements:

- EDT startup through `SwingUtilities.invokeLater`.
- One persistent coalescing `javax.swing.Timer`.
- `WHEN_IN_FOCUSED_WINDOW` bindings for arrows, WASD, and Enter.
- At most one direction change per tick and direct reversal rejection.
- Consistent grid model and pixel rendering.
- Tail-vacating collision semantics.
- One-segment growth and score increment.
- Deterministic empty-cell food selection without a retry loop.
- Full-board win state.
- Score, controls, start, game-over, win, and restart overlays.
- Packed, centered, non-resizable frame.

### Independent reviews

- A log-audit agent reviewed the two Qwen runs and confirmed the controller failed closed.
- A repair agent implemented and compiled the corrected source.
- A separate source-review agent returned PASS for the final static logic.

### Not proven

- Keyboard behavior in every desktop/window-manager environment.
- Visual appearance at different scaling/DPI settings.
- Long-running interactive behavior.
- Every reachable self-collision sequence through manual play.

Compilation and static review must not be reported as interactive runtime testing.

## Tradeoffs accepted

| Decision | Benefit | Cost |
|---|---|---|
| Exactly one action per response | Atomic approval, clear evidence, safe replay | More slow inference turns; models naturally try to batch work |
| Strict parsing | Examples/reasoning cannot silently execute | Understandable but malformed responses are rejected |
| Six tools, no shell | Lower tool-selection entropy and smaller attack surface | Cannot launch/drive the Swing UI or run arbitrary project commands |
| Unlimited output by default | No silent truncation of valid code | Weak models can loop; experiments need an explicit ceiling |
| Explicit experiment output ceiling | Bounded runtime for tests | A too-small ceiling may truncate a valid large edit |
| Archive full history, retain three bounded messages | Fast, deterministic active context with durable evidence | Older detail requires archive lookup or a fresh `read_file` |
| Controller-owned build argv | Model cannot inject a shell command | Only built-in project profiles are supported |
| Java compilation as required evidence | Deterministic Java 8 compatibility signal | Does not prove semantic or GUI correctness |
| Conservative file-path extraction | Avoids false artifact requirements | Extensionless requested artifacts may need dynamic discovery |
| Invalidate checks after edits | Completion refers to latest source | More build turns and latency |
| Independent repair after experiment failure | Produces a useful example without falsifying results | Final artifact is not evidence that the local model passed |

## Alternatives rejected

- Executing the first action from a response containing several actions.
- Treating natural success prose as completion after a failed build.
- Permissively parsing any JSON or tool-like text found in reasoning.
- Raising temperature randomly after failures.
- Giving the model an unrestricted shell to compensate for missing checks.
- Claiming the independently repaired game as a successful Qwen result.
- Keeping all historical source/diff content in the active prompt.
- Treating compilation as proof of gameplay correctness.

## Evidence-retention lesson

The temporary raw validation directories were removed after independent audit to avoid committing
large model responses, snapshots, and generated class output. The run ids and relevant event
sequence findings are preserved above.

Future benchmark runs should retain a sanitized evidence bundle containing:

- Configuration and model hash/name.
- Prompt text.
- Event-type/timing table.
- Compiler stdout/stderr.
- Final source hash.
- Redacted failure samples.
- Independent verdicts.

Raw logs may contain user source or secrets and should not be committed by default.

## Final interpretation

The experiment validated the safety controller more strongly than the coding capability of the
model. The system correctly refused unsafe ambiguity and unsupported success, but the Qwen3.5-9B
CPU workflow was too slow and semantically unreliable for this task. The next optimization target
is not more tools; it is a smaller active context, a cleaner action protocol, model/provider-aware
thinking control, and reproducible benchmarks.
